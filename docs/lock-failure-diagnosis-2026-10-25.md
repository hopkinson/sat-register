# 锁位失败排查与验证码判据修正（2026-10-25）

## 会话恢复更新

### 人工验证自动接续修复

原实现中，`attemptSelection` 遇到验证码未完成会直接返回，worker 随后只等待浏览器关闭；它不会持续检测人工验证后的状态。因此此前“完成后自动接续”的说明不准确。已将该阶段接入 worker 的 `waitForManual`，真实控件完成且当前确认页考期、考点仍与任务一致时立即继续选座，不依赖聊天回复时间。

本轮相关检查 15/15 通过，覆盖人工验证后继续一次、错误日期／考点不放行、未验证不提交、HTTP 原样提交及停止等待。新版已加载并重新恢复任务。

后续接续时先读取任务 `selection` 和最新日志、提交探针；任务可能已在用户回到聊天前完成一次提交。不能仅因网页后来回到登录页就重新启动报名或清除结果。

用户回复“已完成”时，原浏览器已回到官网登录页，SDK 与提交探针也已不在原报名页面，不能把旧答复当作新会话验证完成。已重新登录并恢复到同一考期／考点，新任务加载了修正后的 hCaptcha 判据；只观察提交的探针也已重新安装。

新增竞态保护：后台识别返回后，如果官网控件已先完成验证，保留官网结果，不注入稍后返回的令牌。验证放行依据实时控件状态，不依赖后台识别的返回标记。对应相关检查 11/11 通过，包含“人工先完成、后台后返回”场景。

已请用户在新会话再次完成验证码。当前等待人工正常验证，不会凭旧会话状态提交。

恢复后的真实任务已到同一确认页，SDK 响应长度仍为 0，提交探针为空；没有把用户的旧答复当作新会话已通过。新版已加载，任务为 `needs_action`，浏览器保留。新增相关检查 11/11，既有验证码选座集成及恢复／停止检查 5/5，均已通过。

## 当前结论

尚不能把 `assignSeat failed` 归因于考位容量、报名数据或官网服务。先前“hCaptcha 已通过”的结论范围过大：旧代码通过 React `onVerify` 回调写入令牌、解禁 Continue，就报告成功；本轮现场却发现 SDK `getResponse()` 为空、复选框为 false，挑战层一度仍遮挡按钮。应用层状态改变不能证明验证码控件完成。

官方缓存前端 `070_captcha-2pgs_M3E.js` 显示，选座请求字段 `fingerprint` 来自 hCaptcha 上下文，由 `onVerify` 更新。此前将该字段归为 kiwi 设备指纹、进而解释 500 的说法没有独立验证，已纠正。保留 kiwi 官网资源加载，不据此断言它是锁位失败的根因。

官方前端 `137_test-center-CK7Saifc.js` 会把 `RegAdminTestCenterService.assignSeat failed` 映射为通用无位文案，因此页面的“seat is no longer available”也不能独立证明具体业务原因。

## 已修正代码

- 移除选座请求参数去重改写和 HTTP 500 后的实验性 POST 重放；仅观察官网原样请求。
- HTTP 提交失败保留 HTTP 状态、错误消息及请求编号，返回已有 `unverified` 状态，优先于通用无位文案；不进入失位重试。
- 不再记录完整请求体、验证码令牌或认证头，仅保留考点、考期、assessment 数量等诊断摘要。
- 确认步骤复用现有点击处理；导航后的响应体日志读取有等待上限，避免诊断阻塞成功跳转。
- hCaptcha 必须同时满足：SDK 有响应、挑战层不再可见、真实确认按钮可用。按钮不存在、仅回调解禁或仅 textarea 有值均不算完成。
- 验证未完成时直接交接，禁止继续提交选座，不再绕过遮挡强制点击。
