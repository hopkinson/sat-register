## 2026-10-23 17:40 选座无反应的根因（已定位两个真实 bug）

用临时探针（挂 `window.open` / `history.pushState` / `XMLHttpRequest`）抓到点击后的真实行为：**点击是有效的，它发出 `POST https://satreg-api.collegeboard.org/msregrequest-prod/student/get-order-line-items`。**

| 现象 | 根因 | 处置 |
| --- | --- | --- |
| 点 8 a.m. 后页面毫无反应、无导航、无报错 | 该接口**经本机 HTTP 代理会一直挂起**（直连 0.6s 返回，代理下连接失败）；页面在等响应，等不到就什么都不做 | `proxyConfig` 增加 `bypass`，默认绕过 `satreg-api.collegeboard.org`，可用 `SAT_PROXY_BYPASS` 覆盖。改后实测接口 **200 + appToken** |
| 首次运行报"未出现账号输入框"直接转人工 | 官网记住邮箱后登录页**只有密码框**，引擎只认邮箱输入框就判定登录不可用 | 增加 password-only 分支：无邮箱框但可见密码框时直接填密码 |
| 规则页一直"未找到 Continue 按钮" | 真实 Continue 是 `<a>` 不是 `<button>` | 选择器加 `a:visible:has-text("Continue")`（已验证 3 次） |

验证码同理：Arkose 挑战从未出现，原因是选座链路没打通，不是密钥问题。

## 验证码自动识别已接入（同日 14:40 实施）

`yescaptcha-solver.js` 原本是孤儿模块，现已接入 `sat-engine.js`：

- `solveCaptchaOnce(page, onLog)`：读取全局 `yescaptchaKey` → 从 Arkose iframe 的 src 提取 publicKey（提取不到用模块默认值）→ 提交 `FunCaptchaTaskProxyLess` → 拿到 token 后 `injectArkoseToken()` 注入（隐藏表单域 / `window.arkose` 对象 / `arkose:token` 自定义事件三种常见接收方式）→ **以验证码控件本身消失或隐藏为唯一通过判据** → 通过则继续选座链路，未通过如实转人工。
- 接入点：`checkVerification()`（轮询中发现验证码）和 `attemptSelection()`（选座后弹验证码，通过则继续确认页→照片→结账链路）。
- 配额保护：每次任务运行最多自动识别 2 次、两次间隔 ≥60 秒，用完后保留浏览器转人工，避免无谓消耗打码次数。
- 诚实降级：注入不被页面接受、打码服务失败、未配置密钥，都如实记录并交接人工，不谎称通过。判据特意不用"确认页文本"——验证码正是在确认页上弹出的，文本一直都在（测试固化了这个坑）。
- 测试：新增 2 个用例（识别全链路含公钥提取/注入接受/不接受/服务失败/无密钥五条路径；选座场景集成），`npm test` 32/32 通过。
- **待实测**：token 注入方式是否被 CollegeBoard 当前页面接受，需要一次真实 Arkose 挑战才能证实；届时看日志里的"注入点"与页面是否推进即可判断，不行再补对应 hook。
